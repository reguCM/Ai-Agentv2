# AI-Agent 開発 Step 1

## Agent Runtime / 状態管理の土台を作る

### 目的

現在開発中の Local AI-Agent に、今後の Tool Calling、Test Runner、Verification、Recovery、Model Registry などを安全に追加できるようにするため、まず Agent Runtime の基本的な状態管理を導入する。

今回は大規模な作り直しを行わない。

**現在動いている機能をできるだけ維持しながら、「Agentが現在何をしているのか」をプログラム側で管理できる状態を作ることを最優先とする。**

# 2. 今回の状態管理の考え方

Agentの外側に `Agent Runtime` を置く。

重要なのは、

**LLM自身に状態管理を任せないこと。**

状態はPython側で管理する。

概念的には以下。

```text
User
 ↓
Agent Runtime
 ↓
LLM
 ↓
Tool Calling
 ↓
Tool
 ↓
Verification
 ↓
Agent Runtime
 ↓
LLM
 ↓
Final Answer
```

Agent Runtimeが現在の状態を保持する。

---

# 3. 最小限の状態を定義する

最初から大量の状態を作らない。

まず以下程度でよい。

```text
IDLE
THINKING
TOOL_CALL_REQUESTED
TOOL_RUNNING
TOOL_SUCCESS
TOOL_FAILED
OBSERVING
COMPLETED
ERROR
CANCELLED
```

実際のコードでは、文字列を直接ばらばらに使用せず、Enum等を使用して管理すること。

例：

```python
class AgentState(Enum):
    IDLE = "idle"
    THINKING = "thinking"
    TOOL_CALL_REQUESTED = "tool_call_requested"
    TOOL_RUNNING = "tool_running"
    TOOL_SUCCESS = "tool_success"
    TOOL_FAILED = "tool_failed"
    OBSERVING = "observing"
    COMPLETED = "completed"
    ERROR = "error"
    CANCELLED = "cancelled"
```

ただし、既存コードとの整合性を確認してから実装すること。

---

# 4. Agent Runtimeを作る

可能であれば専用モジュールを作る。

例：

```text
runtime/
├── __init__.py
├── agent_runtime.py
└── state.py
```

ただし、現在のプロジェクト構造により適切な場所がある場合は、それを優先する。

Agent Runtimeには最低限、

* 現在状態
* セッションID
* 実行中Tool
* Tool実行回数
* 最後のエラー
* 状態変更履歴

を保持できるようにする。

---

# 5. 状態遷移を記録する

例えば、

```text
IDLE
 ↓
THINKING
 ↓
TOOL_CALL_REQUESTED
 ↓
TOOL_RUNNING
 ↓
TOOL_SUCCESS
 ↓
OBSERVING
 ↓
THINKING
 ↓
COMPLETED
```

のような履歴を残せるようにする。

最低限、

```python
{
    "state": "tool_running",
    "timestamp": "...",
    "tool": "get_gpu_status"
}
```

のような情報を記録できればよい。

---

# 6. 現在のTool Callingへ接続する

既存のTool Callingを作り直さない。

現在の処理に対して、状態変更を追加する。

例えば、

```text
LLMへ問い合わせ
↓
THINKING
↓
Tool Callを検出
↓
TOOL_CALL_REQUESTED
↓
Tool実行開始
↓
TOOL_RUNNING
↓
Tool成功
↓
TOOL_SUCCESS
↓
結果をLLMへ渡す
↓
OBSERVING
↓
再度LLM
↓
THINKING
↓
最終回答
↓
COMPLETED
```

という流れを作る。

---

# 7. Tool失敗時も状態を記録する

Toolが例外を返した場合、

```text
TOOL_RUNNING
 ↓
TOOL_FAILED
 ↓
ERROR
```

など、現在の状態を正しく残す。

この段階では高度なRecoveryやRetryをまだ実装しなくてよい。

ただし、

**「失敗したことをRuntimeが認識できる」**

ところまでは作る。

# 12. 将来のTest Runnerを考慮する

ただし、Test Runnerを後から追加しやすい構造にする。

将来的には、

```text
Chat UI
  │
  ├── 通常のAgent実行
  │
  └── Test Runner
          ↓
       Agent Runtime
          ↓
       Tool / LLM
```

という構造にする予定。

そのためAgent Runtimeは、

**「チャット専用の処理」にならないようにする。**

通常チャットでもTest Runnerでも利用できる共通Runtimeとして設計する。

# 14. 実装方針

重要事項：

* 既存機能を壊さない
* 大規模なリファクタリングをしない
* 現状調査を先に行う
* 最小限の変更で実装する
* 新しい機能にはテストを付ける
* 日本語コメント・ログを優先する
* 技術上必要な識別子は英語のままでよい
* 不明点がある場合は勝手に仕様を決めず、質問する
