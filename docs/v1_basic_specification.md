## 0. 本文書の位置付け

| 文書 | 役割 |
|------|------|
| 構想書（基本設計書） | 長期理念・原則・意図的未決定・将来像 |
| `docs/current_system_specification.md` | **いまのコード事実** |
| **本仕様書（V1）** | **V1で何を満たせばよいか／何をやらないか** |

V1 は「完成した自律Agent」ではない（構想§29・§34）。  
V1 は、将来の自己改善へ進むための**土台が、実際に動く形で存在する**ことである。

改訂時は:

1. 構想の将来項目を自動で V1 必須にしない  
2. 現状仕様書と矛盾する「実装済み」主張をしない  
3. 能力試験の合否を V1 完了の唯一条件にしない（経路と評価可能性を優先）

## 1. V1 の目的（スコープ内）

V1 の目的は次に限定する。

> ローカルLLMを用いた開発パートナーの**最小実行可能基盤**を用意し、  
> 人間（必要に応じて Cursor / 上位LLM）と分担しながら、  
> **能力の試験・問題発見・改善を繰り返せる**状態にする。

V1 で目指す到達点（構想§29をV1向けに絞り込んだもの）:

```text
能力の一部が動く
  → テストできる
  → 結果を記録できる（誰が実行したかを含む）
  → 問題を分類できる
  → 人間側で原因究明・改善できる
  → 改善をコードに反映できる
  → 再テストできる
```

Agent が**単独で**原因究明〜改善実装〜評価方法の改訂まで完遂することは **V1必須ではない**（構想§5・§14・§18の「将来」側）。

## 2. V1 に含めないもの（明示的アウトオブスコープ）

構想書にあっても、V1 必須仕様には**持ち込まない**。

| 構想由来の将来機能 | V1での扱い | 理由 |
|--------------------|------------|------|
| 完全自律の連続実装ループ | 対象外 | 構想§10・§17は実績後 |
| 自己改善の自動実行（提案だけでなく適用） | 対象外 | 構想§18は理想；§5は完成前に期待しない |
| 評価方法そのもののAgent自動改善 | 対象外 | 構想§18後半・§31 |
| 成功率90%による自動昇格 | 対象外 | 構想§16は目安；§31で未決定 |
| ランタイムでの上位LLM（GPT）相談API | 対象外 | 構想§4.3；完成前は運用で代替（§5） |
| PLAN_GATE（複数経路の開始前承認）の必須化 | 対象外※ | 有用だが未実装；V1必須にしない（Clarityで代替可能） |
| 単一入口への強制統合（agent.py≡全Pipeline） | 対象外 | 現状二入口；統合は別判断 |
| Tool v1/v2 正式版管理・自動昇格 | 対象外 | 構想§21；未実装 |
| Tool廃止・隔離保存の自動化 | 対象外 | 構想§22–23；§31 |
| ストレージ三領域の自動管理 | 対象外 | 構想§23 |
| 経験のRAG本格利用・NN再学習 | 対象外 | 構想§25–26；§31 |
| 開発/商業/特化安全の3タイプ製品分岐 | 対象外 | 構想§30は将来構想 |
| Observation Validator の必須化 | 対象外 | 現状未完了；V1必須にしない |
| 「Webで常に正解を答えられる」こと | 対象外 | 構想§13は評価観点；完遂をV1完了条件にしない |

※ PLAN_GATE は V1 の**任意改善候補**とし得るが、無いことをもって V1 不合格にはしない。

## 3. V1 の前提（役割分担）

### 3.1 開発段階（必須の認識）

V1 期間中の主開発は次とする（構想§5）。

> **人間 + Cursor +（必要なら）上位LLM**

ローカル Agent に高度な自己修正を**要求しない**。

### 3.2 役割

| 主体 | V1での役割 |
|------|------------|
| 人間 | 目的提示、仕様・安全・権限の最終判断、能力評価、重大承認 |
| PROJECT_AGENT（`agent.py`） | 要求の一次処理、公開Toolの選択・実行、結果に基づく応答（可能な範囲） |
| RESEARCH_PIPELINE | Tool開発・Research・Judge・実装検証の重い経路（ベンチ/スクリプト入口を含む） |
| Cursor / 上位LLM | 実装・原因分析・改善の支援（**運用**。Agent能力実績に加算しない） |

「Agent」とだけ書いて主体を曖昧にしない。報告は `docs/current_system_specification.md` §2・§12 の主体名に従う。

## 4. V1 アーキテクチャ仕様（現状を正規とする）

V1 は、理想の単一ループへ無理に統合することを要求しない。

### 4.1 二入口を V1 正規形とする

| 入口 | 規範パス | V1で担うこと |
|------|----------|--------------|
| PROJECT_AGENT | `agent.py` | Clarity → Agent公開Tool → 応答。実行主体ログ |
| RESEARCH_PIPELINE | 例: `research/llm_benchmarks/research_implement.py` | 新規Toolに関する調査・実装・検証のパイプライン |

統合は V2 以降の設計判断とする。

### 4.2 Registry 公開契約（V1必須）

- Tool は `registry/tools.json` に登録する  
- `visibility=agent` のみ PROJECT_AGENT の Ollama tools に載せる  
- `visibility=pipeline` は Pipeline / 内部工程用（Agent LLM に誤公開しない）  
- Agent 公開 Tool は schema（必須引数含む）と実装シグネチャを一致させる  

### 4.3 実行主体の記録（V1必須）

- PROJECT_AGENT / RESEARCH_PIPELINE の起動・Tool実行を区別して記録できること（`execution_identity`）  
- Judge に主体を推測させない  
- Cursor の検証結果を PROJECT_AGENT 実績に合算しない  

### 4.4 LLM

- 実行時 LLM はローカル Ollama 経路（`tools/system/llm.py`）  
- モデルは `config/pipeline.yaml` + `config/llm_models.yaml`、必要時 `AI_AGENT_MODEL` で上書き  
- V1 は特定モデル名の固定を必須としない（プロファイルで管理）

## 5. V1 機能要件（必須）

### 5.1 要求の一次明確化

- Clarity（または同等）により、成果物レベルの曖昧さを扱う  
- 実現手段の選択をユーザーに丸投げしない（`project_context.implementation_method_selection: Agent` の方針を維持）  
- 非TTY等で確認不能なら安全側に停止してよい  

### 5.2 PROJECT_AGENT の公開能力

V1 で Agent 公開として維持・整備するカテゴリ:

| カテゴリ | V1要件 |
|----------|--------|
| ローカル観測 | GPU/CPU 等、既存の実測Toolを実行できる |
| Workspace File | list / read / search。root外禁止・サイズ上限 |
| Web検索 | **実際に検索を実行し結果を返す経路**があること。品質完遂は§6 |

Tool 結果は LLM へ raw で返せる（stdout要約の失敗で能力経路を止めない。F-001方針）。

### 5.3 RESEARCH_PIPELINE（Tool開発）

- 不足能力に対し、設計〜調査〜実装〜検証のパイプラインを**人間監督下**で実行できること  
- `web_research` は検索実行ではなく材料化であること（責務分離を維持）  
- Pipeline 用 `research.web.search_web` の技術調査向け挙動を、Agent一般検索の都合で壊さない  

### 5.4 安全（V1最小）

- 重大操作・生成コード実行等について、既存の Safety / Gate / 人間決定フックを維持する  
- **PROJECT_AGENT の Tool 実行はデフォルト人間確認**（`tools/system/agent_tool_gate.py`）。未昇格は確認、人間が確認不要と判断した Tool のみ `auto_allow` 昇格。降格可。Research Pipeline の Safety とは**統合しない**  
- 安全装置・承認ルール・権限の変更は人間の明示承認が必要（構想§19）。V1で自動化しない  
- 既存Toolの無秩序な上書きを防ぐ（版管理の完成は対象外だが、破壊的変更は人間確認）  
- 危険度の完全分類は V1 で完成させない。使用実績を後の判断材料とする  

### 5.5 記録

- 実行主体・Tool名・引数・結果ダイジェストを残せる  
- Research/ベンチ結果をファイルに残せる（形式の統一は段階的でよい）  
- 「蓄積を優先し利用方法は後」でよい（構想§24・§31）

## 6. Web検索（V1の扱い）

### 6.1 V1必須

- PROJECT_AGENT から Web 検索 Tool を呼べること  
- Pipeline 技術検索と Agent 一般検索の**責務分離を壊さない**こと  
- 評価時に実行主体を区別できること  

### 6.2 V1必須にしない

- あらゆる現在情報質問への正解保証  
- 特定トピック（例: 時事の固有名詞）のハードコード  
- 構想§13の「答えられた」成功を、V1完了の唯一ゲートにすること  

### 6.3 V1での評価方針

- 代表例の最小セットでよい（構想§13）  
- 成功候補: 要求に答えられた  
- 失敗は種類分けする（情報なし／参照しない／到達不能等）  
- 失敗時の改善主体は V1 では人間+Cursor+上位LLM（構想§14）  

Web品質（旧F-002系統）の追加実装は、別チケットで扱う。本V1仕様は「経路と評価可能性」までを必須とする。

## 7. 要望から実装まで（V1の最小フロー）

V1 で要求する最小フロー:

```text
要望
 → Clarity（成果物の明確化）
 → （人間確認が必要な場合）停止または確認
 → 実行:
      A) 既存Agent公開Toolで応答可能 → PROJECT_AGENT
      B) 新規Toolが必要 → RESEARCH_PIPELINE（人間監督）
 → 結果の記録
 → 必要なら人間が仕様・コードを更新
```

構想§6の「選択肢の詳細比較表→仕様書確定→人間最終確認」の**完全形は V1必須ではない**。  
ただし次は V1 で守る:

- 仕様の無断書き換え禁止（問題時は案提示→人間承認→文書更新）  
- 「どうすればいいですか？」だけの丸投げを避ける（Clarity / 推奨案の方向）

## 8. 成功・失敗（V1定義）

### 8.1 成功

個別タスクの成功は原則:

> **そのタスクの要求に対して答えられた／成果物要件を満たした**

「エラーが無い」「コードが出た」だけでは成功としない（構想§15）。

### 8.2 失敗の扱い

- 改善対象の失敗と、情報非存在・要求不能などは区別する  
- 詳細分類は運用で改良してよい（構想§15・§31）  
- 過去失敗を永久禁止にしない（構想§25）— V1で禁止リスト自動化はしない  

---

## 9. V1 完了条件（受け入れ）

次をすべて満たしたとき、V1基盤として受け入れ可能とする。

1. **二入口と visibility 契約が文書化され、実コードと一致している**  
2. **PROJECT_AGENT が公開Toolを選択・実行し、結果を LLM に返せる**  
3. **RESEARCH_PIPELINE が人間監督下で Tool 開発系ループを実行できる**  
4. **実行主体をログで区別できる**  
5. **安全上の重大変更が人間承認なしに自動変更されない**  
6. **代表的な能力について、人間が再試験できる手順またはテストがある**  
7. **現状仕様書が実コードと乖離したまま放置されない**（改訂ルール遵守）  

次は V1完了に**不要**:

- 完全自律  
- 自己改善の無人実行  
- Web全問正解  
- 単一Agentへの統合  
- 90%昇格ルール

## 10. V1期間中の開発プロセス（規範）

1. 基本機能を動かす  
2. 実際に使う・測る（主体を偽らない）  
3. 問題を発見し分類する  
4. 人間+Cursor+上位LLMで改善する  
5. 仕様書（現状／V1）を必要なら更新する  
6. 十分な実績がある領域だけ、将来バージョンで自動化を検討する  

（構想§32を V1運用に落としたもの）
