# AI Development Session Start Policy v1

## AI開発 作業開始・再同期規定

## 1. 目的

本Policyは、Cursor、Codex、AntiGravity、Local Agent等を利用した開発において、

- 前回の古い状態を現在状態と誤認する
- 完了済み作業を再実装する
- 別branch / 別worktreeで誤って作業する
- 他AIが行った変更を知らずに上書きする
- 古い指示書をそのまま再実行する

ことを防ぐための、作業開始・再同期ルールを定める。

本Policyは毎回の細かな作業指示で必ず実行するものではない。

**作業開始・再開・状態確認など、再同期が必要な場面で発動する予防的Policy**とする。

---

# 2. 基本原則

AIは、

**「前回何をしていたと思うか」ではなく、現在のRepository状態を確認してから作業を再開する。**

ただし、毎回過剰な確認を行わない。

必要な場面だけ再同期を行う。

---

# 3. Session Start Policyの発動トリガー

以下のようなユーザー指示を受けた場合、本Policyを発動する。

例：

- 「今日の作業始めます」
- 「作業開始」
- 「作業再開」
- 「前回の続きから」
- 「状況確認して」
- 「今どこまで進んでいる？」
- 「現在の状態を確認して」
- 「Cursorで続きをやる」
- 「Codexで続きをやる」
- 「AntiGravityで続きをやる」
- 「しばらく空いたので再開する」

完全一致である必要はない。

**ユーザーの意図が「開発状態を再確認してから進みたい」である場合に発動する。**

---

# 4. 発動しない例

以下のような通常の継続指示では、原則としてSession Start確認を繰り返さない。

例：

- 「そのテストも追加して」
- 「次にこれを直して」
- 「さっきの結果を説明して」
- 「この関数も確認して」
- 「そのまま続けて」

同一セッション内で状態が明確に連続している場合、再同期は不要。

---

# 5. 軽量Session Check

通常の作業開始・当日再開・簡単な状況確認では、まず軽量確認を行う。

最低限：

1. 現在worktree
2. 現在branch
3. HEAD
4. staged
5. unstaged
6. untracked
7. 直近の関連commit
8. 現在の主要作業テーマ

必要であれば、

- 前回完了報告
- 関連する最新仕様書
- 最新テスト結果

も確認する。

確認後、

### READY

そのまま作業可能

### RESUME

未完部分だけ継続可能

### ALREADY_DONE

前回指示はすでに完了済み

### NEED_FULL_SYNC

より詳細な再同期が必要

のいずれかを判断する。

---

# 6. Full Session Sync

以下の場合は完全再同期を行う。

- 日付をまたいだ
- 数時間以上空いている
- 前回から別AIが作業した可能性がある
- Cursor / Codex / AntiGravity等の担当が変わった
- HEADが前回記録と異なる
- branchが異なる
- worktreeが異なる
- 新しいcommitが追加されている
- working tree状態が前回と異なる
- 古い指示書の続きを再開しようとしている
- 状態が不明
- ユーザーが「状況確認して」と明示したうえで現在状態が複雑

Full Syncでは以下を確認する。

1. Repository / worktree path
2. branch
3. HEAD
4. staged
5. unstaged
6. untracked
7. 最新commit一覧
8. 前回記録HEAD
9. 前回以降の新規commit
10. 前回未完作業
11. 完了済み作業
12. 関連する正本仕様
13. 現在のテスト状態
14. 他AIによる変更の可能性
15. 今回指示が現在も有効か

---

# 7. 時間概念

時間は再同期の補助情報として扱う。

可能な範囲で以下を確認する。

- 現在日時
- 前回作業終了日時
- 最新commit日時
- 関連ログの最終更新日時

ただし、

**「何時間空いたか」だけで作業可否を決めない。**

重要なのは、

**その時間の間にRepository・仕様・実行状態が変化した可能性**

である。

短時間でもHEADが変わっていれば再同期する。

長時間空いていてもRepository状態が完全一致している場合は、その事実を確認して再開してよい。

---

# 8. 前回指示書の扱い

前回の指示書が与えられていても、

**その内容が現在も未完であると仮定してはならない。**

まず確認する。

- すでに実装済みか
- commit済みか
- 別AIが完了させたか
- 後続作業で仕様が変わったか
- 現在branch / worktreeが正しいか
- 現在HEADにその変更が含まれているか

完了済みの内容は再実装しない。

部分完了なら未完部分だけ継続する。

---

# 9. Worktree確認

複数worktree運用時は、Session Start時に必ず現在位置を確認する。

例：

`D:\AI-Agent`

と

`D:\AI-Agent-worktrees\tool-result-contract`

を混同しない。

別worktree向けの指示を誤ったworktreeで実行しない。

---

# 10. 正本の優先順位

状態判断では、原則として以下を優先する。

1. 現在Repositoryの実状態
2. 現在branch / HEAD
3. Repository内の正本仕様・Policy
4. 最新の完了報告
5. 現在のユーザー指示
6. 過去の指示書
7. AI自身の過去セッション記憶

古い指示書と現在コードが矛盾する場合、勝手に古い状態へ戻さない。

---

# 11. Git Policyとの関係

Git操作は、

`docs/GIT_OPERATION_POLICY.md`

に従う。

Session Start Policyは、

**「何を始めてよいか」**

を判断する。

を判断する。

---

# 12. Session Start確認前の禁止

再同期が必要と判断された場合、確認完了前に以下を行わない。

- コード変更
- file overwrite
- git add
- commit
- branch切替
- merge
- push
- reset
- clean
- restore
- 古い仕様への巻き戻し
- 前回の続きだと推測した実装

---

# 13. 作業開始判定

確認後、以下のいずれかを宣言する。

### READY

現在状態と指示が一致しており作業開始可能。

### RESUME

前回作業の一部が未完であり、未完部分のみ継続可能。

### ALREADY_DONE

指示内容はすでに完了している。

### CONFLICT

現在状態と指示が矛盾しているため実装停止。

### UNKNOWN

状態を確定できず追加調査が必要。

---

# 14. 簡易報告

軽量Session Checkでは、長い報告を毎回行う必要はない。

通常は以下だけでよい。

```text
Session Check: READY

worktree:
branch:
HEAD:
Git状態:
前回からの主な変更:
今回の作業:
```

問題がある場合だけ詳細を報告する。

---

# 15. ユーザーによる明示的トリガー

ユーザーが簡単にSession Start Policyを発動できるようにする。

推奨例：

### 今日の開始

「今日の作業始めます」

→ 軽量Session Checkを実行する。

### 状況確認

「状況確認して」

→ 現在状態を確認し、必要ならFull Syncへ昇格する。

### 前回再開

「前回の続きから」

→ 前回指示が現在も未完か確認してからRESUME判定する。

### 完全確認

「完全に再同期して」

→ Full Session Syncを実行する。

---

# 16. AI側からの自動発動

ユーザーが明示していなくても、以下を検出した場合はAI側からSession Checkを行ってよい。

- branch不一致
- HEAD不一致
- worktree不一致
- 想定外の大量差分
- 他AIによる新規commit
- 指示対象がすでに実装済み
- 古い指示書との明確な矛盾

ただし、問題がない同一セッション内で頻繁にSession Checkを繰り返さない。

---

# 17. 基本運用

本Policyの目的は確認作業を増やすことではなく、

**長時間の開発や複数AI利用でも、古い状態を誤認して壊さないこと**

である。

通常はユーザーが、

「今日の作業始めます」

「状況確認して」

などと簡単に伝えるだけでよい。

AIは必要な確認範囲を判断し、問題がなければ短くREADYを返して作業へ進む。

---

# 18. 他AI・別セッションによる継続作業

別AI・別セッションによる変更を検出した場合、それだけを理由に`CONFLICT`または作業停止としない。

現在Repositoryを正本として、**前回の作業目的がどこまで進展したか**を確認する。

判定は以下を優先する。

### ALREADY_DONE

前回の未完作業が、別AIによって既に完了している。

再実装せず、最新実装・テスト・commitを確認して次工程へ進む。

### RESUME

別AIが前回作業を途中まで進めている。

既存成果を保持し、未完部分だけ継続する。

### READY

前回作業が正常に完了しており、新しい工程へ進める。

### CONFLICT

以下のように継続が危険な場合のみ使用する。

- 正本仕様との矛盾
- 前回目的と逆方向の変更
- 同一箇所への競合実装
- どちらを採用すべきか判断不能
- 継続すると既存成果を壊す可能性が高い

## branch / worktree

前回と異なるbranchまたはworktreeを検出しても、即座に元へ戻さない。

まず、以下を確認する。

- 前回作業の継続先として作られたものか
- 最新commitがどこに存在するか
- 前回の未完作業がそこで進んでいるか

正しい継続先が別branch / worktreeである場合は、そちらを現在の正しい作業場所として扱う。

## 基本思想

「前回と違う」こと自体は異常ではない。

まず、**進展したのか、競合したのか**を判定する。

別AIが正常に作業を引き継いで完成させた場合、古い状態へ戻さない。
