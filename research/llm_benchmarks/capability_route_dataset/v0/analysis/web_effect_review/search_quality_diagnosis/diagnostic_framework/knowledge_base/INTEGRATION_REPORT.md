# INTEGRATION_REPORT — ここまでの実験から分かっていること

対象: `search_web` 品質まわりの LLM 診断実験（コード読解・仕様・経路分解・証拠境界・N2・DeepSeek・大型LLM）。  
本レポートは **既存成果の統合のみ**。新規実験・本番修正・既存結果の改変は行っていない。

---

## 1. 一文での結論

診断品質は「モデルの頭の良さ」だけでは決まらず、**入力（ctx・コード添付・route 分解）と証拠境界・ゲート**が同じくらい支配する。小型LLMは局所解析に使え、大型LLMは統合と偽原因棄却で有望だが、**どちらも自動修正の既定にはできない**。

---

## 2. 実験の流れ（何を試して何が分かったか）

1. **データのみ診断** → 粗い優先は出るが経路帰属は弱い。コード読解が必要になった。  
2. **汎用フレームワーク／自己検証** → `num_ctx` や code_pack 欠落で「コードが無い」と誤診しうる。ハーネス設計が第一級の問題だと判明。  
3. **コード読解（32768）** → 入口・backend・ranking 関数は読める。一方 **stdout 要約（約 L520）と `json.dumps` handoff の混同**、collect と ranking の混同、存在＝原因が残る。  
4. **仕様書 v1/v2** → 物語理解は一部改善。実装行帰属の本丸は解けない。仕様改良だけでは臨界項目で明確勝利しない。  
5. **route 分解** → 表示経路と LLM 経路を分けると接続テストは改善しうる。caller 誤認・原因過信は残る。  
6. **collect/rank 分離 × 証拠4分類** → OBSERVED 捏造抑制は有効。原因リストの過信は残る → N3 仮説。  
7. **N2** → 経路外フィルタ専用。経路上の誤因果は通す。フル経路物語は過信を増やしうる。  
8. **DeepSeek** → 全面置換は不十分。長プロンプトは ctx 超過。共有失敗モードは残る。  
9. **大型LLM（Composer）** → 当該問題セットで経路分離・偽原因棄却・UNKNOWN が改善。auto_fix は NOT_ALLOWED。一般化は未検証。

詳細索引: [EXPERIMENT_INDEX.md](./EXPERIMENT_INDEX.md)

## 4. 有効だった方法 / 有効ではなかった方法

**採用〜条件付き採用（範囲付き）**

- FACT / OBSERVED / INFERENCE / UNKNOWN — 原則常時（捏造抑制）  
- route 分解（表示 vs LLM）— handoff 疑い時  
- collect / ranking 分離 — 段階境界疑い時  
- N2 — 経路外候補の存在フィルタのみ（原因強度には使わない）  
- 小型LLM — 局所解析・一次候補  
- 大型LLM — 構造化後の統合・監査（有望／条件付き）

**単独では不十分・または不支持**

- 仕様書だけで実装帰属を正す  
- DeepSeek への診断 LLM 全面置換  
- 「コードをたくさん渡す」だけで原因診断が正しい  
- N2 YES を強い原因とみなす  
- 大型LLMだから自動修正してよい

**未検証だが有望**

- N1（1接続ずつの Yes/No）  
- N3（ログなし runtime 原因の断定禁止）  
- 材料圧縮 → 小 ctx モデル  
- 小型局所 → 大型統合の正式パイプライン  
- 診断方法の自律選択そのもの

手法表: [METHOD_EFFECTIVENESS.md](./METHOD_EFFECTIVENESS.md)

## 5. モデル性能とハーネス設計の分離

観測された成否は次の積に近い。

```text
結果 ≈ モデル × num_ctx/実効入力長 × パック設計 × 証拠ラベル × ゲート × 設問設計
```

例:

- Qwen の「コードが読めない」の一部は **4096 / 未添付**（ハーネス）だった。  
- DeepSeek の失敗の一部は **長プロンプト超過**であり、コード読解力だけの比較ではない。  
- 大型の改善は **読んだ範囲と条件Bの独立性** を含む。モデル名だけで一般化しない。

詳細: [MODEL_COMPARISON.md](./MODEL_COMPARISON.md)

## 7. 将来の自己診断への含意（暫定）

状況に応じて方法を選ぶ知識は [SELF_DIAGNOSIS_SELECTOR.md](./SELF_DIAGNOSIS_SELECTOR.md) に整理した。  
手順の仮案は [DIAGNOSTIC_WORKFLOW.md](./DIAGNOSTIC_WORKFLOW.md)。

現時点で言えること:

- **証拠境界と入力設計は常に先**（モデル交換より先に効くことが多い）。  
- **小型で全部を決めない／大型でも未承認修正をしない**。  
- 「小型→ゲート→大型→人間」は **有望な暫定アーキテクチャ**であり、確定仕様ではない（README 参照）。

言えないこと:

- 大型なら自己診断できる（一般化未検証）。  
- セレクタを実装すれば自律修復まで行ける（未検証）。  
- search_web の本番品質問題が単一原因で解けた（本統合は診断方法の知見統合であり、修正実験ではない）。
