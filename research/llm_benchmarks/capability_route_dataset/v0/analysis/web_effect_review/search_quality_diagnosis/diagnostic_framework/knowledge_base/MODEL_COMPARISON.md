# MODEL_COMPARISON

**モデル性能**と**入力設計・ワークフロー性能**を分離して記す。  
「どれが一番強い」への単純化はしない。

---

## Qwen3:8b

| | |
|--|--|
| 長所 | 比較的長い診断プロンプトを処理できる事例が多い。入口・backend・ログケース列挙が安定しやすい |
| 短所 | stdout と LLM handoff の混同、collect/ranking 混同、存在＝原因、根拠行ずれ、原因過信 |
| 適した仕事 | 局所コード断片の説明、ログの機械観測の言語化、一次候補の列挙 |
| 危険な仕事 | 一括での最終原因断定、自動修正許可、経路全体の caller 確定を単独で任せる |

---

## DeepSeek-Coder-V2 16B

| | |
|--|--|
| 長所 | 短文の経路接続で `json.dumps` 行を当てる例あり |
| 短所 | 長い診断入力で ctx 超過。ログ照合・UNKNOWN・存在＝原因で弱点。短縮するとログ捏造リスク |
| 適した仕事 | （条件付き）短い Yes/No 接続確認の試行 |
| 危険な仕事 | Qwen と同一の長文一括診断の置き換え、ログ付き原因診断の単独担当 |

**結論（実験）:** 診断 LLM の全面置換は **単独では不十分**。

---

## 大型LLM（Cursor Auto / Composer）

| | |
|--|--|
| 長所 | 同一 search_web 問題セットで経路分離・偽原因棄却・UNKNOWN・反証が Qwen より良好だった（条件B） |
| 短所 | 他 Tool・盲検再実験・自動修復への一般化は未検証。コスト・運用は別問題 |
| 適した仕事 | 構造化された FACT/候補の全体統合、監査、修正可否判断 |
| 危険な仕事 | 生の長い未整理ログだけでの断定、承認なし自動修正 |

---

## 分離して読むべきこと

```text
観測された改善
  = f(モデル能力, プロンプト/ctx, route分解, 証拠境界, ゲート, 人間評価)

「大型だから正しい」ではない。
DeepSeek 失敗の主因の一つは入力長であり、コード読解力だけの比較ではない。
```

---

## 有望な役割分担（仮説・未確定）

```text
小型LLM
  ↓ 局所的なコード・ログ解析
構造化された FACT / 候補
  ↓
安全ゲート（N2/N3 等）
  ↓
大型LLM
  ↓ 全体経路統合・原因候補比較・修正可否
人間承認
```

これは **有望な仮説**（FINDINGS F011）であり、確定仕様ではない。
