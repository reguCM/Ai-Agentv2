# search_web 設計仕様 v2（地図と調査原則）

この文書は **設計意図の地図** と **コードを読むときの原則** である。

次のものは書かない。実装の答えはコードから取る。

- 具体的なソースファイル名
- 行番号
- 「この関数が LLM への受け渡しである」といった断定
- 実験問題の正解

検証するときは次を分離する。

| 層 | 意味 |
|----|------|
| SPEC | 設計上こうあるべき／こう意図している |
| CODE | 実装上こうなっている（コードを読んで確認する） |
| OBSERVATION | 実行するとこうなった（ログ） |
| INFERENCE | 上記から推測されること（断定しない） |

SPEC は CODE の証拠ではない。SPEC と CODE が食い違う場合は **CODE を優先**して記録する。一致するかどうか自体を調査してよい。

---

## 調査原則（v2 で追加）

### 原則A：存在と使用を区別する

コード上に処理があることは、「存在する」ことしか意味しない。

その処理が、公開 Tool の実行経路で **実際に呼ばれている** とは限らない。

経路上にあると判断する前に、次を順に確認する。

```text
定義 → 呼び出し元 → 呼び出し先 → 戻り値 → 次の処理
```

定義だけ見て経路に含めてはならない。

### 原則B：データの受け渡しを追跡する

変数・戻り値・JSON・標準出力・ログ・画面表示が同じ対象に見えても、同じデータ経路とは限らない。

特に次を混同しない。

- ログ出力
- デバッグ表示
- CLI / 端末表示
- ユーザー向け要約
- Tool の戻り値
- 次の推論でモデルが読む入力

「データが表示されている」ことと、「その表示処理の結果がモデルへ渡されている」ことは別問題である。

ある値がモデルへ渡ると判断するには、その値が **会話上の Tool 結果（または同等の入力）に代入・追加されている** ことをコードで確認する。確認できなければ不明とする。

### 原則C：呼び出し関係を確認する

ある処理が経路上にあると言うには、最低限次を確認する。

1. 誰が呼んでいるか
2. 何を引数として渡しているか
3. 戻り値は何か
4. 戻り値を誰が受け取るか
5. その値が最終的にどこへ行くか

確認できない矢印は「不明」とする。推測で経路を補完しない。

### 原則D：同名・類似処理を混同しない

次のような語が複数箇所にあっても、同一経路とは判断しない。

search / ranking / filter / compact / result / output / JSON / display / stdout / dump / serialize

「JSON を作っている」ことは、「モデルへ渡す JSON を作っている」ことの証拠ではない。
「結果を短くしている」ことは、「検索候補を除外している」ことの証拠ではない。
「検索」と名の付く別モジュールが、公開入口と同じ経路であるとは限らない。

### 原則E：仕様書と実装の役割を分離する

- 仕様書: 何をする設計なのかを理解する地図
- コード: 実際に何をしているかを確認する証拠

仕様書に「結果をモデルへ渡す」と書いてあっても、**どの処理がその役割か** はコードの呼び出し関係から確認する。仕様書から実装を逆算しない。

## 目的（設計）

公開 Tool としての `search_web` は、エージェントが **一般のウェブ情報をその場で調べる** ための入口である。

- 材料化（キャッシュした調査メモの再利用）ではない。
- 別目的の同名検索（特定ドキュメント優先など）とは **別経路** である、という設計である。公開入口が後者を呼ぶかどうかはコードの import と呼び出しで確認する。

---

## 入力（設計）

| 入力 | 役割 |
|------|------|
| 検索クエリ | 各検索 backend へ送る文字列。必須。空なら検索しない、という設計。 |
| 件数上限（任意） | 呼び出し元へ返すヒット件数の上限。省略時は複数件の既定、という設計。 |
| ユーザー要求 | Tool 本体の引数ではない。エージェントまたは診断用スクリプトがクエリを決める材料。 |

クエリの自動翻訳は Tool 本体の設計に含めない。診断用スクリプトがクエリ案を出すことは Tool 仕様の外である。

---

## 検索経路（設計上の段階）

関数名・行番号はコードで確認する。設計上の流れは次のとおり。

```text
ユーザー要求
  ↓（エージェントまたは診断スクリプトがクエリを決める。Tool 外）
検索クエリ
  ↓
公開入口
  ↓
一般ウェブ検索の本体
  ↓
複数 backend へ問い合わせ
  ↓
短い hit 形式へ整形
  ↓
明らかに空の候補は集めない
  ↓
重複の整理
  ↓
関連性に基づく順位と件数の切り詰め
  ↓
辞書として呼び出し元へ返す
  ↓
エージェントが実行結果を受け取る
  ↓
  ├─ 人間が端末で見るための表示・要約（ありうる）
  └─ 次の推論でモデルが読む内容（ありうる）
```

この分岐の **どちらがモデル入力か** は仕様書では断定しない。呼び出しと代入をコードで追う。

URL 先のページ本文を二次取得する段階は、この地図には置かない。実装にあるかどうかは、公開経路からの呼び出しを見て判断する。無いなら無いと書く。推測で補完しない。

---

## 各段階の目的（設計）

| 段階 | 設計上の目的 |
|------|----------------|
| クエリ決定 | 何を調べるかを文字列にする（Tool 外の場合あり） |
| 入口 | 空クエリや件数指定を受け、本体へ渡す |
| backend | 候補の題名・短い説明・URL を外部から得る |
| hit 整形 | 後段が同じ形で扱えるようにする。短い説明は API が返したものであり、ページ全文とは限らない |
| 収集時の欠落除外 | 題名も説明もないものを候補にしない |
| 重複整理 | 同じ場所を指す候補の重複を減らす |
| 順位付けと件数制限 | 関連しそうなものを上位にし、返す件数を抑える |
| 戻り値 | ヒットと試行 backend、エラー情報を呼び出し元へ渡す |
| 表示 | 人間向けに短く示すことがある。モデル入力と同一とは限らない |
| モデルへの材料 | 実行結果を次の推論の材料にすることがある。どの値が渡るかはコードで確認する |

「別系統の関連性フィルタ」が公開経路にあるかどうかは、呼び出し関係で確認する。名前が似ているフィルタを同一視しない。

## 設計意図（なぜ存在するか）

1. **即時検索**: 公開ウェブの短いヒットをその場で足す。
2. **複数ソース**: 一つの取得が空でも、別ソースの候補が残る余地を残す。
3. **短い hit**: ページ全文を取る設計にはしない方向。コストと複雑さを抑える。
4. **件数抑制**: 内部では複数寄せてから返す件数を制限しうる。
5. **失敗の扱い**: ある取得の失敗で全体を止めない方向。自動的な再試行を地図の必須段階には置かない。再試行が実装にあるかは、公開経路の呼び出しで確認する。
6. **表示と推論**: 端末向けとモデル向けは分かれうる。同一視しない。
7. **診断スクリプトは別物**: レビュー用のクエリ提案や埋め込みは本番 Tool の仕様ではない。

---

## この仕様が答えないこと

- どのファイルの何行がモデルへ値を渡すか
- どの関数が JSON 文字列化しているか、その文字列の行き先
- 順位付けの点数表
- 「特定種類のクエリだけ空を返す」といった、地図に無い特殊分岐の有無（有無はコードで判定する）
