# SELF_DIAGNOSIS_SELECTOR

将来 LLM／ハーネスが「どの診断方法を使うか」を選ぶための **知識ベース**。  

暫定実装: `../selector/`（**ルールベース＋知識ベース**。機械学習分類器ではない。LLM 自律選択の検証ではない）。  
実装は問題特徴 → 手法を選び、選択理由・未選択理由・信頼度・再利用成果物を記録する。

効果ラベルは METHOD_EFFECTIVENESS / HYPOTHESIS_STATUS / `method_catalog.json` に対応。

---

## 選択ヒューリスティック（暫定）

```text
症状・問いの型

1) 実行時の挙動／品質がおかしい
   → runtime ログあり?
        YES → OBSERVED をログから記入。原因の発生主張にはログ必須（N3 方向）
        NO  → OBSERVED=なし。runtime 原因の断定禁止

2) ranking と filter（収集）の境界が疑わしい
   → collect と ranking を別 route pack（条件付き採用）

3) stdout と LLM のどちらが問題か不明／handoff 疑い
   → route decomposition（表示パックと messages パックを分離）
   → 可能なら N1（1接続ずつ）（未検証・有望）

4) 原因候補に「本文GET／別Tool filter／retry」等の経路外語
   → N2 存在ゲート（YES≠強い原因）

5) 全体の優先順位・偽原因棄却・修正可否が必要
   → 構造化材料を揃えた上で大型LLMへエスカレーション（有望）

6) 長いログを小コンテキストモデルに渡す必要がある
   → 機械要約を先に（材料圧縮・未検証有望）。無理に全文を押し込まれない

7) 仕様の意図確認のみ
   → 仕様書地図（行番号なし）。実装帰属の最終根拠にはしない
```

---

## 状況 → 方法マトリクス

| 状況 | 優先する方法 | 避けること |
|------|----------------|------------|
| 証拠の種類が混ざる | 4分類ラベル常時 | 推測を OBSERVED に書く |
| handoff 疑い | route 分解 | 一括コードだけで断定 |
| 脱落段階不明 | collect/rank 分離 | 同一パックに押し込み |
| 無いモジュール疑い | N2 | N2 YES を原因確定に |
| ログ無し品質推論 | UNKNOWN / N3 | 架空ログ |
| 最終統合 | 大型＋人間 | 小型単独で auto_fix |
| モデル置換だけで解決したい | — | DeepSeek 全面置換（不支持） |
