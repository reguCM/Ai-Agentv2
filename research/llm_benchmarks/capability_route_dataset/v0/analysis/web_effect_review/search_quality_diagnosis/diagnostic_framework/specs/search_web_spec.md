# search_web 設計仕様（地図）

この文書は **設計意図の地図** である。実装の行番号や、特定の実験問題の正解を記さない。

検証するときは必ず次を分離すること。

| 層 | 意味 |
|----|------|
| SPEC | 設計上こうあるべき／こう意図している |
| CODE | 実装上こうなっている（コードを読んで確認する） |
| OBSERVATION | 実行するとこうなった（ログ） |
| INFERENCE | 上記から推測されること（断定しない） |

SPEC は CODE の証拠ではない。SPEC と CODE が食い違う場合は CODE を優先して記録する。

---

## 2.1 目的

`search_web` は、Project Agent が **一般のウェブ情報をその場で調べる** ための公開 Tool である。

- 材料化（キャッシュした調査メモの再利用）ではない。
- Tool Builder 向けの Microsoft Learn 優先検索（別モジュールの同名関数）とは **別経路** である。Agent 公開の `search_web` は後者を呼ばない、という設計である。

---

## 2.2 入力

| 入力 | 役割 |
|------|------|
| 検索クエリ `query` | 実際に各検索 backend へ送る文字列。必須。空なら検索しない。 |
| `limit`（任意） | LLM へ返すヒット件数の上限。省略時は複数件の既定。 |
| ユーザー要求 | Tool 本体の引数ではない。Agent または診断ハーネスがクエリを決める材料。 |

クエリを日本語から英語へ **自動翻訳する処理は、Tool 本体の設計には含めない**（クエリはそのまま送る）。診断用ハーネスが別途クエリ案を出すことは、Tool 仕様の外である。

---

## 2.3 検索経路（設計上の段階）

実際の関数名・行番号はコードで確認する。設計上の流れは次のとおり。

```text
ユーザー要求
  ↓（Agent または診断ハーネスがクエリを決める。Tool 外）
検索クエリ query
  ↓
公開入口 search_web
  ↓
一般ウェブ検索の本体
  ↓
複数 backend へ順に問い合わせ（DuckDuckGo Instant Answer、日本語 Wikipedia OpenSearch、英語 Wikipedia OpenSearch）
  ↓
各結果を共通の短い hit 形式へ整形（title / snippet / url / backend）
  ↓
title も snippet もないものは集めない
  ↓
URL 等による重複除去
  ↓
クエリとの文字列一致に基づく順位付けと、返す件数への切り詰め
  ↓
辞書（query, hits, backends_tried, error 等）として返す
  ↓
Agent が Tool 実行結果を受け取る
  ↓
  ├─ 画面表示用の要約（人間が端末で見る）
  └─ 会話上の Tool 結果として LLM が次ターンで読む内容
```

URL 先 HTML の二次取得（ページ本文スクレイプ）は、この経路の設計に **含めない**。

---

## 2.4 各段階の目的

| 段階 | 設計上の目的 |
|------|----------------|
| クエリ決定 | 何を調べるかを文字列にする（Tool 外の場合あり） |
| 入口 | 空クエリ・件数指定を受け、本体へ渡す |
| backend 問い合わせ | 候補の title / 短い説明 / URL を外部 API から得る |
| hit 整形 | 後段が同じ形で扱えるようにする。snippet は API が返した説明文であり、ページ全文ではない |
| 収集時の欠落除外 | title も snippet もないものを候補にしない |
| 重複除去 | 同じ URL（またはそれに準ずるキー）の重複を減らす |
| 順位付けと件数制限 | クエリに関連しそうなものを上位にし、返す件数を抑える |
| 戻り値 | 呼び出し元へ hits と試行 backend、エラー情報を渡す |
| Agent 表示 | 人間向けに短く示す（LLM 入力と同一とは限らない） |
| Agent → LLM | 検索の実行結果を、次のモデル推論の材料にする |

「関連性キーワードで落とす」専用の、Tool Builder 用フィルタは **Agent 公開 search_web の設計段階には置かない**。公開経路の除外は、上記の収集条件・重複除去・順位と件数制限の範囲で考える。

---

## 2.5 重要な設計意図

1. **即時検索**: モデルの記憶やローカル文書だけでなく、公開ウェブの短いヒットをその場で足す。
2. **複数ソース**: 一つの API が空でも、別 backend の候補が残る余地を残す。
3. **短い hit**: ページ全文は取らない。コストと複雑さを抑え、snippet があればそれを使う。
4. **件数抑制**: 内部では複数寄せてから、返す件数を制限する（`limit=1` でも内部収集は複数になり得る、という意図）。
5. **失敗の扱い**: ある backend の例外は蓄積し、他を続ける。ヒットが一つでもあれば「結果あり」として返す、という方向。HTTP の自動リトライは設計に含めない。
6. **表示と推論の分離**: 端末に出す要約と、モデルが読む Tool 結果は、意図として分けうる。どちらが LLM 入力かは **コードで確認する**。
7. **診断ハーネスは別物**: レビュー用スクリプトがクエリを提案したり hits をプロンプトに埋め込んだりしても、それは本番 Tool の仕様ではない。

---

## 2.6 この仕様が答えないこと（意図的）

- 具体的なソースファイルの行番号
- シリアライズ関数の名前と呼び出し箇所
- ranking スコアの点数表
- 「技術クエリのときだけ空を返す」といった、設計に無い特殊分岐

それらは CODE 層の作業である。
